# v1.17.1 — отдельный OAuth-токен Метрики

Дата: 2026-10-04. Репозиторий: `D:\github\directai-mcp` (1.17.0 → 1.17.1).

Задача: Метрика (чтение и запись целей) больше не использует токен Директа —
у неё отдельное приложение Яндекс OAuth (`metrika:read` + `metrika:write`) и
свой ключ в Credential Manager. Client secret приложения в DirectAI не
хранится: OAuth-поток, как и для Директа, проходит в браузере, токен вводит
владелец.

---

## 1. Хранение и выпуск токена

| Что | Значение |
|---|---|
| Ключ Credential Manager | `directai-mcp-metrika` (рядом с `directai-mcp` для Директа; ключ намеренно другой) |
| Переменная окружения | `DIRECTAI_METRIKA_TOKEN` (имеет приоритет) |
| Команда | `directai-mcp set-metrika-token --login <логин>` |
| Что печатает команда | `client_id` приложения Метрики, redirect URI `https://oauth.yandex.ru/verification_code`, права `metrika:read`, `metrika:write`, ссылку на OAuth и предупреждение «в чат токен не пишите» |
| Ввод токена | скрытое поле (`getpass`), значение не печатается и не логируется |
| Client secret | приложению DirectAI не нужен и не хранится — OAuth проходит в браузере |

Константы приложения (`METRIKA_APP_CLIENT_ID`, `METRIKA_OAUTH_REDIRECT`,
`METRIKA_APP_SCOPES`) живут в `config.py` и используются только для
инструкции и проверок.

## 2. Выбор токена

Новые поля `Ctx`: `metrika_token`, `metrika_token_source`
(`metrika` | `direct`) и два метода:

- `metrika_read_token()` — отдельный токен, иначе токен Директа + одно
  примечание в ответе («Метрика читается токеном Директа… выполните
  `directai-mcp set-metrika-token --login <логин>`»), которое не
  дублируется при повторных вызовах;
- `require_metrika_write()` — возвращает отдельный токен либо поднимает
  `ValueError` с инструкцией; вызывается первым делом в `prepare` всех трёх
  действий записи и в `verify` (read-back).

Переведены все вызовы Метрики на `metrika_read_token()`:
`counters.py` (`counter_check`, `metrika_goals_list`),
`metrika_reports.py` (все четыре отчёта), `metrika_cpa.py`,
`metrika_goals.py` (`resolve_value_types`), `campaign_journal.py`
(снимок результатов), `cli.py` (сверка основной цели в `check`).

Кеш целей и счётчиков Метрики (кеш процесса) теперь keyed по
`(sha256(токен)[:12], counter_id)` — иначе счётчик, прочитанный токеном
Директа, мог бы отдаться по токену Метрики.

## 3. Проверки: check / doctor / describe_action

- `check` — новая строка «Метрика: …»: источник токена, `client_id`
  приложения (первые 8 символов, через `login.yandex.ru/info`), читается ли
  список счётчиков, и — при отдельном токене — предупреждение, если токен
  выдан не приложением Метрики. Живой вывод сейчас:

  ```
  OK Метрика: токен Директа (только чтение) (приложение 5b70e34c…) запись
  целей недоступна: нужен отдельный токен — directai-mcp set-metrika-token
  --login <логин> чтение OK: счётчиков 28
  ```

- `doctor` — проверка `f. Токены` теперь показывает «метрика: есть/нет», и
  новая проверка `l. Метрика` (12 проверок вместо 11): источник, длина,
  приложение, счётчики; при `--skip-api` сетевой части нет.

  ```
  [OK] l. Метрика: токен Директа (только чтение) (длина 51); INFO: чтение
  токеном Директа, запись целей недоступна → отдельный токен:
  `directai-mcp set-metrika-token --login <логин>`
  ```

- `describe_action` без аргументов — строка «Метрика: …» в блоке статуса
  сервера (собирается в `server.py`, каталог конфиг не читает — правило
  `test_catalog_actions_only_read_guard`).

Значение токена не появляется ни в одном из этих выводов.

## 4. Про `metrika:write`: что можно и что нельзя проверить без записи

Требование было — показать, есть ли `metrika:write`. Живые пробы 04.10.2026
на токене Директа (права записи нет) показали, что API сначала проверяет
существование объекта и тело запроса, и только потом право:

| Проба | Ответ |
|---|---|
| `DELETE /management/v1/counter/0/goal/0` | 404 `Entity not found` |
| `POST /management/v1/counter/0/goals` | 404 `Entity not found` |
| `POST /management/v1/counter/{реальный}/goals {}` | 400 `goal must not be null` |
| `POST /management/v1/counter/{реальный}/goals {цель}` | 403 `access_denied` |

Вывод: **любая проба на несуществующем объекте вернёт 404 и ничего не скажет
о праве** (404 доказывает лишь существование), а проба на реальном счётчике
с валидным телом — это создание мусорной цели. Поэтому «проверка права»
в check/doctor **не выдумана**: вместо неё выводится честное «не
проверяется без записи; право подтвердит первая запись цели», а вместо
этого показывается `client_id` приложения — по нему видно, что Метрике
достался именно токен приложения Метрики. Ошибочный вариант (403 →
«нет права» на основании 404) сначала был написан, проверка показала его
негодность, и он удалён до релиза.

## 8. Что сознательно не сделано

- `metrika:write` не «проверяется» пробой — причина в §4.
- OAuth-обмен кода на токен внутри команды не делается: нужен client secret,
  а хранить его в бинаре нельзя (README §7.1, шаг 3).
- `client_id` приложения Метрики добавлен в репозиторий (он виден в URL
  авторизации и не является секретом); client secret не добавлен.
- Замена токена Метрики на токен Директа «на лету» для уже созданных планов
  не делается: план привязан к источнику токена, и apply перечитает токен
  заново — если токен выпущен уже после создания плана, запись пройдёт с
  новым.
