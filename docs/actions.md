# Каталог действий DirectAI MCP

Сервер даёт 82 действия: 57 на чтение и 25 на запись. Ниже — что каждое
делает, какие у него ограничения и как устроены отдельные группы.

Порядок работы ИИ-агента:

1. `search_actions` — найти действие по задаче;
2. `describe_action` — параметры и пример;
3. `run_read` — чтение, либо `plan_write` → предпросмотр → ваше «да» →
   `apply_write` — запись (см. [safety.md](safety.md)).

`describe_action` без имени (или с пустой строкой) показывает статус
сервера и не тратит баллы API:

- `server_version` — версия, которую декларирует установка пакета
  (`importlib.metadata`);
- `code_version` — код, реально запущенный в процессе;
- `disk_version` — исходники на диске;
- строка «Метрика: …» — какой токен используется для Метрики.

`code_version` ≠ `disk_version` — перезапустите MCP-сервер.
`server_version` ≠ `code_version` — переустановите пакет
(`uv tool install --force --editable .`): у editable-установки метаданные
обновляются только переустановкой, перезапуск не поможет.

### Правила чтения

- `ads_list`, параметр `states`: по умолчанию архивные не возвращаются;
  `states: ["ARCHIVED"]` (или вместе с `ON`/`OFF`/`SUSPENDED`) включает их.
- Фразы возвращаются целиком, включая внутрифразные минус-слова.
  Укороченный показ — только явным `short_phrases: true` и только для
  отображения; raw-данные он не меняет.

## Запись (25 действий)

Все действия записи идут только через план: `plan_write` → предпросмотр →
ваше «да» → `apply_write` → read-back. Прямых записей в обход плана нет.

| Действие | Что делает |
|---|---|
| `campaigns_create`, `campaigns_update`, `campaigns_state` | Создание (по умолчанию ЕПК), изменение (в т. ч. ключевые цели и расписание), остановка/архив кампаний |
| `adgroups_create`, `adgroups_update` | Создание и изменение групп (тип группы — из типа кампании) |
| `ads_create`, `ads_update`, `ads_state` | Создание (для ЕПК — RESPONSIVE_AD), изменение, состояние объявлений |
| `keywords_add`, `keywords_update`, `keywords_state` | Фразы: пакетное добавление, тексты, состояние |
| `negatives_set` | Минус-фразы кампании/групп и общие наборы |
| `extensions_create` | Ссылки, уточнения, изображения |
| `bids_set` | Ставки фраз (поиск и сети) |
| `bid_modifiers_set` | Корректировки: добавить, изменить, удалить (включая RETARGETING) |
| `metrika_goal_create`, `metrika_goal_update`, `metrika_goal_delete` | Цели счётчика Метрики (нужен токен с правом `metrika:write`) |
| `retargeting_list_create`, `retargeting_list_update`, `retargeting_list_delete` | Условия ретаргетинга (только при `[retargeting] write_enabled=true`) |
| `audience_target_add`, `audience_target_state` | Привязка условий к группам, пауза/возобновление/удаление привязок (только при `[retargeting] write_enabled=true`) |

### Аудитории (экспериментально)

Запись выключена по умолчанию (`[audience] write_enabled=false`):

- `audience_segment_from_file` — сегмент uploading из локального CSV/TXT
  (телефоны/email; в API уходят только SHA256-хеши). Имя сегмента —
  только `[TEST DirectAI]*`; файл с несколькими колонками без `id_column`
  отклоняется.
- `audience_segment_delete` — удаление сегмента только `[TEST DirectAI]*`
  по живому имени из API.

Без `write_enabled=true` оба действия отклоняются до API.

### Ретаргетинг

Запись выключена по умолчанию (`[retargeting] write_enabled=false`).
Пять действий: `retargeting_list_create` / `retargeting_list_update` /
`retargeting_list_delete` — условия (цели Метрики, сегменты; удаление —
только неиспользуемых, без префикса `[TEST DirectAI]` нужно явное согласие);
`audience_target_add` / `audience_target_state` — привязка к группам и её
состояние. Исключение аудитории делается не условием, а корректировкой
−100% (`bid_modifiers_set`, вид RETARGETING).

Правила:

- В ЕПК и текстово-графических группах — условия `RETARGETING`
  (цели/сегменты Метрики, сегменты Аудиторий); `AUDIENCE` — для медийных
  групп (краткосрочные интересы допустимы и в ТГО).
- Совместимость привязки проверяется живьём по
  `AvailableForTargetsInAdGroupTypes` условия (ЕПК-группы API v5 видит
  как `TEXT_AD_GROUP`).
- На поиске условие сужает аудиторию (AND с фразами), в сетях —
  расширяет (OR).
- Исключить аудиторию (например, купивших) — только корректировкой
  ставки −100%: «показы этой аудитории будут полностью отключены».
  В конверсионных стратегиях это меняет целевую CPA/ДРР.
- Условие только из NONE-правил годится только для корректировок
  (привязать к группе нельзя).
- Лимиты API: 2000 условий на пользователя, 1000 за вызов; 1–50 правил,
  1–250 аргументов; срок членства 1–540 дней (для целей Метрики);
  не более 50 привязок в ТГО-группе; ставка привязки — ручная стратегия
  (при авто — только приоритет, ставка игнорируется с предупреждением).

## Метрика: отчёты

Все отчёты Метрики — только чтение.

- `metrika_traffic` — визиты, пользователи, отказы, глубина, время,
  достижения цели и CR по источникам. `group_by`: `source` (тип источника),
  `utm` / `utm_full`, `direct` (кампании Директа), `landing` (страница входа),
  `device`, `region`. Фильтры `filter_utm_source` / `filter_utm_campaign`
  (точное совпадение).
- `metrika_goals_report` — строки = цели (достижения, CR); разрез
  `group_by` опционален (те же значения).
- `metrika_bytime` — динамика по дням/неделям (`group: day|week`):
  визиты, отказы, выбранная цель.
- `metrika_direct_cpa` — связка с Директом по кампаниям одного логина:
  расход/клики из Директа + визиты/отказы/цели из Метрики. Колонки:
  кампания, расход, клики, визиты, клики→визиты %, отказы %, цели, CR %,
  CPA = расход / цели. Расхождение кликов и визитов больше 30% —
  флаг «проверить разметку/счётчик».

Общее для отчётов:

- счётчик — `counter_id`, иначе `[metrika] counter_id`, иначе счётчики
  кампаний;
- период по умолчанию — последние 14 полных дней;
- цели по умолчанию — основная (`primary_conversion_goal_id`), иначе все
  цели счётчика;
- атрибуция по умолчанию `lastsign` (видна в шапке ответа);
- `accuracy=full`, семплирование помечается;
- 403 по счётчику — «нет доступа», без падения;
- будущие даты отклоняются до API (код 4001 у Директа).

Сопоставление кампаний в `metrika_direct_cpa` (способ — в колонке «Связь»):
ID → ID+1e8 (у старых кампаний OrderID в Метрике больше CampaignId на сто
миллионов; «Связь» = ID+сдвиг) → точное имя при единственном кандидате
(«Связь» = имя). Несопоставленные — отдельными блоками: кампании логина
без расхода, визиты кампаний других логинов, «Чужие кампании».

## Режим выгрузки (dump)

Любое действие чтения принимает `dump_dir` (папка сессии) и `dump_tag`
(суффикс имени). В этом режиме ответ дополнительно сохраняется в файлы
как есть, без преобразований:

- `<NN>_<action>[_<tag>].json` — конверт ответа: `raw_items` (объекты API:
  деньги в micros, enum, null, вложенность; единственное преобразование —
  ID-ключи `*Id(s)` числом → строкой), `requested_field_names` (по каким
  полям читали), `pagination_complete` (все ли страницы прочитаны — честно
  из пагинации, не дефолт), `truncated` (неполон ли raw),
  `display_truncated` (обрезан ли только показ для чата), `warnings`.
  Примеры: `03_keywords_list.json`, `07_ads_list_morning.json`;
- `manifest.json` — порядок файлов и их sha256 (сборка только по манифесту,
  не по glob);
- `describe_<action>.json` — схема ответа (один раз на действие).

Пример вызова:

```json
{"name": "keywords_list",
 "params": {"account": "client-a", "campaign_ids": [900000036],
            "dump_dir": "C:/work/dump-session", "dump_tag": "morning"}}
```

Основной потребитель — скилл `yandex-direct-campaign-dump-directai`:
он вызывает чтения, собирает `dump.json`, проверяет полноту валидатором
и строит Markdown/Excel. Вручную данные не пересказываются.

## Прогноз ставок и спроса

Только чтение. Live-прогноз по новым фразам идёт без Units — баллы
не расходуются; прогноз по существующим фразам (`KeywordBids.get`)
стоит баллы, см. ниже.

- `keyword_bids_forecast` — по уже добавленным фразам (`KeywordBids.get`:
  `AuctionBids` → объём трафика/ставка/цена, `Coverage` для сетей).
  Ровно один scope (`campaign_id` | `adgroup_ids` | `keyword_ids`),
  ровно один кабинет. Таблица «объём → ставка → цена» плюс медианы цены
  для объёмов 100 и 15.

  ```json
  {"name": "keyword_bids_forecast",
   "params": {"account": "client-a", "keyword_ids": [900000011],
              "include_network": false}}
  ```

- `phrases_forecast` — по новым фразам до добавления (Live v4:
  `CreateNewForecast` → ожидание → `GetForecast` → `DeleteForecastReport`).
  Не более 100 фраз за отчёт, `region_ids[]` обязателен, `currency`
  (по умолчанию RUB).

  ```json
  {"name": "phrases_forecast",
   "params": {"account": "client-a", "phrases": ["окна пвх"],
              "region_ids": [213]}}
  ```

Ограничения:

- ставки не меняются;
- на автостратегиях и ЕПК данные идут с пометкой «ставками управляет
  стратегия, прогноз справочный», при отсутствии — «нет данных аукциона»
  (не ошибка);
- `AuctionBids=null` при RARELY_SERVED, только графических объявлениях
  в группе и всегда для автотаргетинга (показывается отдельно);
- прогноз для новых фраз: не больше 5 отчётов одновременно (ошибка 31),
  хранение 5 часов, готовность до ~60 с (таймаут — `forecast_id` для
  повтора); период API прогноза не поддерживает;
- каждый ответ помечен «прогноз Яндекса, не гарантия» с датой, регионами
  и валютой (НДС — как отдаёт API, без пересчёта); в dump поля аукциона
  не добавляются.

Проверено живьём (10.2026): при поиске `SERVING_OFF` API всё равно отдаёт
`AuctionBids` — показываются справочно с пометкой про отключение поиска;
позиции прогноза — P11..P24, CTR — числом (знак % добавляет рендер).

Баллы: `KeywordBids.get` — 15 плюс 3 за каждые 2000 фраз (оценка в ответе,
факт — в строке `API:`; при коде 152 — понятная ошибка с остатком).
Live-прогноз идёт без Units, баллы не расходуются. Подсказка о прогнозе
есть и в описании `keywords_add`.

## Создание кампаний: ЕПК по умолчанию

- `campaigns_create` создаёт `UNIFIED_CAMPAIGN` (ЕПК, запрос на `json/v501`).
  Старый `TEXT_CAMPAIGN` — только явным `campaign_type="TEXT_CAMPAIGN"`
  с предупреждением «устаревший тип».
- `campaigns_update`: блок стратегии и версия запроса — по типу кампании
  (`UnifiedCampaign`/`v501` для ЕПК).
- `adgroups_create`: тип группы API выводит из кампании; неизвестная
  кампания или тип — отказ до API.
- `ads_create`: для ЕПК используйте `responsive_ads` (`RESPONSIVE_AD`,
  запрос на `v501`); `TEXT_AD` допустим, но API конвертирует его (10251) —
  предупреждение требует подтверждения. Совместимость типа группы и
  кампании проверяется до API. DisplayUrlPath обязателен для обоих типов
  и сверяется в read-back.
- Цепочка создания: кампания → группа → фразы → объявление отдельными
  планами. Модерация (`ads_state moderate`) в цепочку не входит и
  заблокирована guard по умолчанию — только отдельным шагом с явного
  решения пользователя.

## Ключевые цели (`campaigns_update`: `priority_goals`)

Цели и их ценности (`PriorityGoals`) — вход оптимизации, поэтому меняются
тем же планом, что и стратегия: в боевой кампании только в режиме `confirm`
с явным «да» на конкретный план, в `block` — запрещено.

- Формат: список `[{goal_id, value_rub, is_metrika_source_of_value=false}]`.
  `value_rub` — ценность конверсии в рублях (для «Максимум прибыли» —
  маржа); внутрь уходит в микро-единицах (₽ × 1 000 000). Список целей —
  `metrika_goals_list`; `is_metrika_source_of_value=true` API принимает
  только для стратегий с долей расходов (`AVERAGE_CRR`,
  `PAY_FOR_CONVERSION_CRR`).
- Режим один — **замена набора целиком** (`Operation=SET`): не перечислили
  цель — она пропала. Пустой список без явного `priority_goals_reset=true`
  отклоняется до API; `priority_goals_reset=true` — это `PriorityGoals=null`
  (оптимизация на вовлечённые сессии). Оба параметра вместе нельзя.
- Повторяющийся `goal_id`, `goal_id ≤ 0` и `value_rub ≤ 0` — отказ до API.
- Ключевые цели нельзя передавать кампании в пакетной стратегии (и нельзя
  одновременно с ключом пакетной стратегии в параметрах): такую кампанию
  сначала отвязывают (`PackageBiddingStrategy=null` + новая
  `BiddingStrategy`) — DirectAI этого пока не делает.
- Предпросмотр плана показывает цели и ценности «было → станет», read-back
  перечитывает `PriorityGoals` и сверяет их с запрошенными.

## Расписание показов (`campaigns_update`: `schedule`)

Часы работы меняются тем же планом, что и остальные настройки: запись идёт
в `TimeTargeting.Schedule`. В боевой кампании это разрешено (как и
`ExcludedSites`): кампания не перезапускается.

- `schedule`: `{days: [1..7], from_hour, to_hour}` — Пн=1, конец — граница,
  как в интерфейсе: 09:00–18:00 — это часы 9..17. Вместо интервала можно
  дать `hours: [...]` — точный список часов.
- **Меняются только перечисленные дни**, остальные остаются как были:
  «суббота 12–13» не трогает Пн–Пт. Чтобы выключить день — `hours: []`.
  Если в ответе API нет `Schedule` (показы круглосуточно), база считается
  круглосуточной.
- Полностью погасить все дни расписанием нельзя — это пауза кампании
  (`campaigns_state`): такой план отклоняется до API.
- `schedule_off: true` — снять ограничение: показы круглосуточно, все дни.
  Вместе с `schedule` — отказ до API.
- Ставки по часам не поддерживаются: включённый час пишется как 100%.
- `ConsiderWorkingWeekends` и праздники сохраняются из текущих настроек,
  остальное в кампании не трогается.
- Превью показывает итог «было → станет» (со всеми днями), read-back
  сверяет часы по дням.

```json
{"name": "campaigns_update",
 "params": {"account": "active", "campaign_ids": [900000456],
            "schedule": {"days": [6], "from_hour": 12, "to_hour": 13}}}
```

## Цели счётчика Метрики

Запись целей — через Management API `POST|PUT|DELETE
/management/v1/counter/{counterId}/goal(s)`. Нужен отдельный токен
приложения Метрики с правом `metrika:write` (см.
[getting-started.md](getting-started.md#отдельный-токен-метрики)): без него
запись отклоняется до обращения к API. Если права нет, API отвечает 403,
и сервер объясняет, как перевыпустить токен — токен в сообщениях, логах
и чате не появляется.

`counter_id` — точный id счётчика, без разбора кампаний.

| Тип (`type`) | Условия | Особое |
|---|---|---|
| `action` | `conditions=[{operator, value}]`, `operator` = `exact`/`contain`/`start`/`regexp` | JS-событие; `value` — идентификатор события (`ym(...)`) |
| `url` | `conditions=[…]` (те же операторы + `action`/`regexp_action`/`contain_action` для составных целей) | посещение страниц; несколько условий — «ИЛИ» |
| `email`, `messenger`, `search` | `conditions=[…]` | длина значения до 1024 (`email`) / 16384 |
| `phone` | `conditions=[…]` | `hide_phone_number`; значение до 25 символов |
| `file` | `file_all=true` **или** `file_url=…` | ровно одно из двух |
| `social` | `social_all=true` **или** `social_url=…` | ровно одно из двух |
| `step` | `steps=[{type: action\|url, conditions:[…]}]`, 2–5 шагов | составная цель, порядок шагов важен |
| `number` | `depth` (≥ 2) | глубина просмотров |
| `visit_duration` | `duration` (секунды, ≥ 1) | длительность визита |

Общее для всех: `name` (1–255), `default_price` (цена по умолчанию,
не отрицательная), `is_favorite`.

- **Мультицели в Management API нет** — типа `multi` в GoalE не существует
  (мультицель есть только в интерфейсе Метрики). Эквивалент «несколько
  условий через ИЛИ» — несколько `conditions` в одной цели; отдельная
  попытка создать `multi` отклоняется с этим текстом. Типы `chat` и
  `payment_system` в DirectAI не заведены.
- **Проверки до записи** (живое чтение, до обращения к API): право на
  счётчик (`GET counter/{id}` → `permission`: `own`/`edit`; `view` — только
  просмотр, запись отклоняется), лимит счётчика — до 200 целей, и **точный
  дубль**: тот же тип и те же условия → отказ с id и именем существующей
  цели (порядок условий и краевые пробелы не считаются различием; порядок
  шагов составной цели — считается).
- `metrika_goal_update` — частичное изменение (имя, условия, цена по
  умолчанию, `is_favorite`, `depth`, `duration`). В API `PUT` заменяет цель
  целиком, поэтому сервер читает живую цель и собирает полное тело: поля,
  которые вы не меняли, сохраняются. Ничего не меняется — отказ до API.
  Тип цели и её шаги не меняются; автоцели (`e_purchase`, `call`, `form`,
  `conditional_call` и др. — их нет в GoalE) не обновляются и удаляются
  только вручную в интерфейсе.
- `metrika_goal_delete` — необратимо: собранная по цели статистика пропадёт
  из отчётов. План всегда помечается «⚠ ОПАСНАЯ ОПЕРАЦИЯ» и применяется
  только с `owner_confirmed=true` (в любом режиме guard) и
  `acknowledge_warnings=true`.
- Read-back после каждой записи: сервер заново читает цели счётчика и
  сверяет тип, условия и имя (id новой цели — из ответа POST). При таймауте
  или обрыве связи статус `unverified`, запись **не повторяется вслепую** —
  решение принимает перечитанный список целей.

## Статусы поиска

Каждый ответ `campaigns_get`/`campaigns_list` несёт строку
`Статус поиска: <lookup_status>, presence=..., proves_account_empty=...`
и то же в dump-конверте и manifest (`lookup_status`).

| lookup_status | Когда | presence |
|---|---|---|
| `resolved` | объект найден в Campaigns API | `configured` |
| `resolved` | в Campaigns API нет, в Reports есть данные (архив, удалена, чужой доступ) | `statistics_only` |
| `not_observed` | нет ни в API, ни в Reports за проверенный период (период указан в message). Не утверждается, что кампании не существует | `null` |
| `ambiguous` | поиск по имени/подстроке дал больше одного совпадения; возвращаются кандидаты (id, name, state) | `null` |
| `incomplete` | ответ частичный (пагинация/лимит/ошибка части запросов); указано, что не проверено | `null` |
| `failed` | ошибка API/сети; код ошибки Директа, без трактовки как «пусто» | `null` |

Проверка Reports для `statistics_only` — только когда Campaigns API вернул
пусто по явному ID: один лёгкий отчёт (`CAMPAIGN_PERFORMANCE_REPORT`,
`CampaignId`, `Impressions`/`Clicks`, период по умолчанию 90 дней, параметр
`lookup_days` переопределяет). Пустой `campaigns_list` —
`proves_account_empty=false` плюс причины (фильтр, права, логин):
пусто ≠ объекта нет. Запись разрешена только при `resolved+configured`
(guard отклоняет остальное до API).

## Основная цель

Необязательное поле кабинета в `accounts.toml` —
`primary_conversion_goal_id` (пример: `900000123`), и переопределение
по кампании — `[aliases.<имя>.campaigns.<campaign_id>]
primary_conversion_goal_id` (также `[accounts.<имя>.campaigns.<id>]`,
пример: `900000456`).

Приоритет: явный параметр запроса `primary_goal` > кампания > кабинет > нет.

- Валидация: целое > 0; служебные `12`/`13` допустимы, но `check`
  предупреждает с расшифровкой (вовлечённые сессии / все приоритетные цели);
  сверка с целями Метрики — best-effort, отсутствие доступа —
  предупреждение, не ошибка.
- `stats_*` и `stats_compare` возвращают блок
  `Цель: id=..., label=..., source=param|campaign|account|none` рядом
  с атрибуцией; CPA/CR — по этой цели; при `source=none` — CPA по всем
  целям плюс предупреждение «основная цель не задана».

## Журнал кампании

Один Markdown-файл на кампанию: что меняли, почему и что стало
с результатами (`<reports_dir>/journals/<login>/<campaign_id>.md`,
перезаписывается при каждом `campaign_journal`; источник правды —
`journal.sqlite`).

- Привязка операций — таблица `operation_campaigns` (схему `operations`
  не меняли; старые записи привязаны backfill при первом `connect`).
- Снимки результатов — `campaign_snapshots` (`direct`: показы, клики,
  расход, CTR, CPC, конверсии из логики `stats_compare`; `metrika`: визиты,
  отказы, цели, CPA из логики `metrika_direct_cpa`; цель по умолчанию —
  основная; будущие даты отклоняются до API).
- Заметки — `campaign_notes` (`hypothesis|decision|observation|todo`).
- Δ в таблице снимков: Δ = A−B, Δ% от B.

Инструменты: `campaign_journal` (сборка и файл), `campaign_journal_snapshot`,
`campaign_journal_note`, фильтр `get_operation_log(campaign_id=...)`.
Все они читают API, а заметки и снимки пишут только локально — без записи
в Директ и без планов.

Правило для агента: перед оптимизацией прочитать журнал кампании, считать
CPA по основной цели, после работы сохранить снимок за период и заметку
`kind="decision"`.

### Минус-фразы

- `"..."` — запрос только из этих слов; `[]` — фиксированный порядок;
  `!` — словоформа; `+` — обязательность; полное пересечение минуса
  с ключом отменяет минус.
- Проверка конфликтов — в `dump_to_xlsx.py` (функция `neg_match`), тесты
  на вымышленных фразах.

### Атрибуция

| Система | Модели |
|---|---|
| Директ | FCCD, LC, LSCCD, AUTO (прямого соответствия Метрике нет) |
| Метрика (legacy → cross-device с 25.06.2026) | lastsign → cross_device_last_significant и др. |

Фактическую модель Reports API отдельно не возвращает: в `effective`
подставляется запрошенная модель (`effective_attribution`), `source` —
откуда она взялась (`api` — явно в параметрах, `config` — дефолт
`accounts.toml`). `effective=null`, `source="not_reported"` — только если
модели действительно нет. Без целей Reports игнорирует AttributionModels
(фактически LC) — это помечается в ответе отдельно.
