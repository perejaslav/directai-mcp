# Политика решений

Как из данных получаются выводы. Реализация: `scripts/auditlib/rules.py`.

## 1. Три класса утверждений

| Класс | Значение | Обязательные поля |
|---|---|---|
| **Факт** | прямо подтверждается данными | доказательства, объект |
| **Вероятная причина** | согласуется с данными, но есть альтернативы | доказательства, альтернативы, следующий шаг |
| **Гипотеза** | требует проверки | основания, альтернативы, способ проверки |

Запрещено: «конверсии упали, значит проблема в сайте». Правильно:
«конверсии упали на 35%, арифметически основной вклад даёт CR; возможные
причины — спрос, состав трафика, сайт, трекинг; следующий шаг — проверить
сегменты и журнал изменений».

Каждая вероятная причина обязана иметь минимум одну альтернативу.

## 2. Приоритеты

| Код | Смысл | Примеры |
|---|---|---|
| `P0` | критично: сломано отслеживание или модерация | нет счётчика, нет основной цели, отклонённое объявление, разрыв клики→визиты |
| `P1` | существенная возможность с сильным основанием | устойчивое падение конверсий при достаточных данных, минус-фраза рубит целевой трафик |
| `P2` | плановая оптимизация | площадка выше порога без конверсий, дорогой сегмент, запрос без заявок |
| `P3` | наблюдение, гигиена, эксперимент | площадка ниже порога, дубли фраз, информационный запрос |

Приоритет **не** определяется только суммой расхода. Высокий расход при слабых
данных остаётся `P2`/`P3`.

## 3. Уверенность

| Код | Когда |
|---|---|
| `high` | прямое подтверждение: настройка, статус, точная сумма, проверенный конфликт |
| `medium` | признаки есть, но возможны альтернативные объяснения |
| `low` | гипотеза, мало данных |

Числовая вероятность не присваивается: без статистической модели это
выдумка. Где модель применима, приводится p-value и объём выборки.

## 4. Ожидаемый эффект

Разрешены четыре формы:

1. `technical` — подтверждённый технический результат («объект прошёл модерацию»);
2. `estimate` — оценка с методом и условиями (например, расход площадки за
   период при полном исключении);
3. `qualitative` — направление без числа («CTR может вырасти»);
4. `none` — «недостаточно данных для оценки».

Число допускается только в `estimate` и только с непустым `method`.
Формулировки «сэкономим 30 000 ₽» запрещены: это оценка, а не гарантия.

## 5. Деньги: три разные величины

| Величина | Что это |
|---|---|
| **Фактический расход** | подтверждённая сумма по объекту за период A |
| **Расход под риском** | расход объекта, чья эффективность под сомнением |
| **Потенциальная экономия** | оценка сокращения будущих расходов при выполнении условий |

Правила:

- суммы по пересекающимся объектам не складываются: группа ⊃ фраза ⊃ запрос;
  при смешении уровней общая сумма не считается (`sum = null`), остаются
  подытоги по типам;
- экономия всегда `conditional: true` и с методом;
- расход под риском не равен экономии.

## 6. Структура рекомендации

Обязательные поля: проблема, объект, доказательства, приоритет, уверенность,
предлагаемое изменение, ожидаемый эффект, риск, способ выполнения, способ
проверки.

Способ выполнения — `tool` (подтверждённое действие записи, только предложение)
или `manual` (интерфейс, сайт, Метрика). Аудит не выполняет ни то, ни другое.

Способ проверки содержит: базовый период, контрольные метрики, ожидаемое
направление, условия достаточного объёма, побочные эффекты, критерии успеха
и неуспеха.

## 7. Минус-фразы

Кандидат предлагается, только если:

1. запрос потратил ≥ порога и дал 0 конверсий;
2. слово-кандидат **есть в самом запросе**;
3. слово входит в заданный контекст исключений (`session.product.exclude_terms`);
4. минус действительно блокирует запрос (все слова присутствуют);
5. минус не игнорируется из-за полного пересечения с целевой фразой;
6. минус не блокирует запрос, который уже даёт конверсии;
7. слово не входит в защищённый список (цена, отзывы, обзор, купить…).

Если хотя бы одно условие не выполнено — не рекомендация, а гипотеза
«проверить вручную». Пример: «работа монтажником окон» и минус «вакансии»:
слова «вакансии» в запросе нет, значит показ не будет исключён.

## 8. РСЯ

- площадка без конверсий **не** попадает автоматически в запрещённые;
- порог `2 × CPA` — ориентир внимания;
- выше порога → кандидат на разбор, ниже → наблюдение;
- исключение площадки выполняется вручную: текущий список `ExcludedSites`
  через API не читается, автоматическая замена опасна.

## 9. История изменений

- журнал даёт последовательность событий, не причинность;
- изменение в периоде A рядом с падением метрики — это `HIS-01` с оговоркой;
- если похожее изменение уже выполнялось, рекомендация получает пометку
  «проверить результат перед повтором»;
- в журнал решений пишутся только решения пользователя.

## 10. Чего делать нельзя

- объявлять гипотезу фактом;
- называть корреляцию причиной;
- подставлять нули вместо пропусков;
- выдавать оценку за гарантию;
- считать заявку продажей;
- выводить прибыль из одного CPA;
- придумывать инструмент записи, которого нет в реестре.
