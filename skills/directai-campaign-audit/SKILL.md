# DirectAI Campaign Audit

## Goal

Разобрать одну кампанию и выдать план улучшений. Только чтение:
никаких записей, пауз, ставок и бюджетов из этого скилла.
План действий — списком с указанием инструмента записи, БЕЗ выполнения.

## Порядок работы

Параметры входа: логин (account, по умолчанию active), ID кампании,
период для `stats_compare` (по умолчанию последние 14 дней vs предыдущие 14).

1. `campaigns_get` — настройки, стратегия, регионы, счётчик, цели,
   основная цель (`primary_conversion_goal_id`: param > campaign > account > none).
   Перед оптимизацией — `get_operation_log` (что уже меняли через DirectAI).
2. `stats_compare` — динамика по умолчанию 14 vs 14 дней (явные даты
   `period_a_from/to` + `period_b_from/to`, пресетов периода у него нет;
   A — свежий период, B — прошлый).
3. Детализация: `stats_adgroups`, `stats_ads`, `stats_keywords`,
   `stats_search_queries`, `stats_placements` (если есть показы в сетях),
   `stats_devices`, `stats_regions`.
4. Гигиена: `negatives_audit`, `extensions_list`, `moderation_check`,
   `counter_check`, `bid_modifiers_get`.
5. Для фраз с показами при ручных ставках — `keyword_bids_forecast`.
   Для новых фраз спрос/цены — `phrases_forecast` (только чтение).
6. Проверки — строго по `references/checklist.md` (порог + что сказать).
7. Выход — файл `reports/audit_<login>_<campaign>_<дата>.md` (не коммитить,
   `reports/` в .gitignore) + итог и план в чат + вопрос, какие пункты выполнить.

## Правила (общие для обоих скиллов v1.11)

- Бюджеты кампаний не менять никогда.
- Любая запись — только через штатный цикл
  prepare (`plan_write`) → подтверждение пользователя → apply (`apply_write`)
  → read-back. Из скилла аудита записей нет — только предложить пункты плана.
- Сравнение периодов — только `stats_compare`, не двумя вызовами с ручной арифметикой.
- Длины текстов — по лимитам Директа (пакет «Знания»), проверять до prepare.
- DisplayUrlPath (отображаемая ссылка) — всегда заполнять и проверять в read-back.
- Вывод пользователю: русский, простым языком, кратко.
- Метрики из вывода инструментов (CTR, CPC, CPA, CR, Δ, доли) не пересчитывать
  вручную — брать как есть. Режим целей и атрибуцию цитировать из шапки
  инструмента, не формулировать своими словами.
- Пусто ≠ объекта нет: пустой ответ не доказывает отсутствие.
- CPA/CR — по основной цели. Дни недели — только через `group_by=weekday`,
  почасового среза нет.
- Guard-блокировка — защита, а не ошибка: остановиться и сообщить пользователю.

## Выходной файл

`reports/audit_<login>_<campaign>_<дата>.md`:

1. Итог в 3 строках.
2. Цифры — таблица `stats_compare` с правилом Δ: Δ всегда = A−B (свежий минус
   прошлый: рост со знаком +, падение −), Δ% = (A−B)/B × 100 — делить
   на прошлый период B (в т.ч. для п.п.-метрик CTR/CR/отказы). Если инструмент
   отдал B−A или Δ% от базы A — пересчитать в отчёте и подписать формулу
   под таблицей (исключение из правила «не пересчитывать»).
   Конверсии и CPA во всём отчёте — только из `stats_compare`; цифры срезов
   (`stats_adgroups`, `stats_ads`, `stats_keywords`, `stats_search_queries`,
   `stats_placements`, `stats_devices`, `stats_regions`) — только для
   долей/распределения, с пометкой об этом.
3. Проблемы по важности (со ссылкой на пункт checklist).
4. План действий: пункты с указанием инструмента записи
   (`negatives_set`, `keywords_state`, `ads_update`, `extensions_create`,
   `bid_modifiers_set` и т.д.), БЕЗ выполнения.

В чат — итог + план; спросить, какие пункты выполнить.
Пример — `references/example-audit.md` (все данные вымышлены).
